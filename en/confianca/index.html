Trust & security

What the platform does with your data — and what it does not do

An engineering result is not worth anything because it looks right: it is worth what can be proven about it. This page says how every number comes out verifiable, where the data lives, who can see it, and what we do not have yet.

Every claim below points at the code or the document behind it.

Pillar 01

Every result carries its own proof

Each execution stores the evidence record: requested and resolved parameters, versions (library commit and runtime packages), hardware, logs, resources consumed (wall and CPU time, peak memory, exit code, limits) and the files with a SHA-256 for each.

  • Every verification is pass, fail, inconclusive or not_run — a check that did not run never counts as passed.
  • The record is pass only if at least one verification checked the result and all of them ran and passed.
  • The report comes out in Markdown with every parameter and where it came from: your text or the documented default with its source.

Pillar 02

A model trains only on approved data

The training gate is closed by default: a dataset needs a recorded technical approval and an immutable storage receipt, checked against its SHA-256, before any training. Without it, training is refused.

  • Geometry, mesh and fields go through a unit check before they enter.
  • The catalogue keeps each set's provenance: origin, licence and hash.
  • When a model is approved, the signature records who approved it and under which conditions.

Pillar 03

Where the data lives

Three deployment modes: managed, private VPC and on-premises. A private deployment does not come up without a managed key (KMS), network isolation, audit into immutable storage, backups and a declared restore procedure.

  • The deployment region has to be among the declared data-residency regions, or the configuration is rejected.
  • Credentials enter only as secret-manager references (vault://, secret://, aws-secretsmanager://); an inline DSN is refused at validation.
  • Artifact retention runs as a dry run by default; deleting needs explicit operator enablement and never follows a symbolic link.

Pillar 04

The language model decides nothing on its own

Structuring the request uses a local model (Ollama) when one answers and deterministic rules when none does. An external provider enters only if the operator configures it. A number the model returns is kept only if it is written in the request.

  • Input text goes through an inspection that blocks private keys, tokens and secrets before processing.
  • The answer never returns the matched secret text.
  • Every engineering decision is recorded with the rule that took it.

Stated gaps

What we do not have yet

Publishing only what is ready is cheaper than answering for a promise later. Today we do not have:

If any of these is a requirement for you, say so in the first conversation: it goes into the scope of your contract instead of becoming a surprise later.

  • SOC 2 or ISO 27001 certification.
  • A published external penetration-test report.
  • A status page with an availability history.
  • A published contractual availability SLA.

Security

Reporting a vulnerability

Do not open a public issue. Send a private report to the maintainers, or open a draft GitHub security advisory, with a description, impact, steps to reproduce and affected versions.
